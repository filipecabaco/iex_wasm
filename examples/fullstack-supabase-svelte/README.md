# Full-stack Supabase + Svelte

A local development environment that runs **inside your browser**. Based on `examples/supabase`:
its native Postgres, PostgREST and Auth stack remains unchanged. This example adds Node, Svelte 5,
SvelteKit, Tailwind and shadcn-svelte, a disk-source import bridge, and a private static preview.
You edit ordinary project files with an editor on your computer, not a browser text editor.

## Start

```sh
go build -o snowglobe ./cmd/snowglobe
./snowglobe build examples/fullstack-supabase-svelte --out dist/fullstack-supabase-svelte
./snowglobe serve dist/fullstack-supabase-svelte
```

Open the page directly in **desktop Chrome/Edge**, on HTTPS or localhost. The 2-CPU VM reserves
1,280 MiB RAM, plus browser/runtime overhead; this is a desktop-oriented example. The isolation
service worker can reload the page once before the VM starts.

1. **Choose working folder…** selects a small, trusted source project folder. Browsers show its
   name, not the full OS path. Do not select your home directory or a folder containing secrets.
2. For a **completely empty** folder, click **Create starter in empty folder…** and confirm.
   This writes ordinary source/config/lock files to disk, without overwriting existing files,
   and builds the preview. A failed initialization can leave a partial starter; the UI reports
   the error rather than deleting those files. You can recover manually in your local editor.
3. Open that same folder in VS Code, another editor, or a local agent. The starter has a working
   notes app: create an account, add/delete notes, and sign in as another user to test RLS.
4. After saving edits in your editor, click **Sync & preview**. It reads the disk sources,
   replaces the VM's `/workspace` mirror, reconciles dependencies, and runs `node --run build`.
   No source files are written back to disk by sync. VM-only npm manifest changes must be saved
   with **Save package manifests to disk** first, so sync cannot silently discard them.
5. Click **Open preview** to show the app in a panel alongside the terminal. **Reload preview**
   reloads the current build; **Close preview** unloads the app without stopping the VM. Another
   sync closes the panel; reopen it after a successful build. There is no automatic disk watcher
   or Vite HMR. Keep this page foreground while building or using the app: browsers throttle hidden
   VM tabs (a controlled test measured about fivefold lower CPU throughput), which can cause Auth
   request deadlines to expire. Builds can take several minutes on the emulated CPU.
   Native diagnostic builds of the lightweight starter took about three minutes; browser timings
   depend on the host. The compiler has a ten-minute deadline, and dependency installation has
   a separate ten-minute deadline. Failures never publish a partial build.
6. Reopening remembers the chosen handle. **Reconnect folder** requests permission if needed.
   Always sync current disk contents before previewing after a page refresh or checkpoint restore.

## Pinned toolchain

Versions were selected from the npm registry's stable `latest` tags at implementation time:

- Svelte **5.57.2**, SvelteKit **3.0.1**, adapter-static **4.0.0**, Vite **8.3.4**.
- Tailwind / Tailwind Vite plugin **4.3.3**.
- shadcn-svelte CLI **1.7.0**, Bits UI **2.19.5**, Supabase JS **2.117.3**.
- TypeScript **6.0.3**: the current `svelte-check` peer contract does not accept TypeScript 7.

`app/package-lock.json` pins the complete dependency tree. SvelteKit 3 moves configuration into
`vite.config.js`, uses `$app/tsconfig`, and replaces the default `$lib` alias. The starter explicitly
retains `$lib` for shadcn compatibility. The shipped button, card, input, label, textarea and badge
components are generated by the official shadcn CLI (nova style), not lookalike components.
The theme, `components.json`, Bits UI, icons and utility libraries are included for adding more UI.
The default form uses accessible native labels to avoid visiting the entire Bits UI barrel graph
just for labels; the real generated Label component remains available. Startup primes Node's supported
module compile cache in the guest so workers can reuse bytecode with the same CPU/version tag.

The image seeds a mutable dependency cache at **`/home/supa/dependencies/node_modules`**, outside
of the replaceable source mirror. `/workspace/node_modules` links to that cache. No npm installation
is required on your computer for the starter. Do not copy Linux VM dependencies onto your computer,
or import your computer's platform-specific `node_modules` into the VM.

## Add npm packages

In the VM terminal, after connecting and syncing your project:

```sh
cd /workspace
npm install zod
# Or: npm install -D a-dev-package
# Or: npm uninstall zod
```

The workspace npm wrapper installs into the **real cache directory**, not the `/workspace`
symlink. Only successful operations return updated `package.json` and `package-lock.json` to
`/workspace`. Click **Save package manifests to disk** to commit those two files to your local
project, then **Sync & preview**. No `node_modules` folder is written to disk by that button.
Both files are checked for outside edits before the first write, and checked again at each commit.
If a commit fails partway through, the UI identifies files already saved; it cannot atomically
commit two separate OS files. Reconcile conflicts in your editor rather than overwriting them.

Matching disk manifests reuse the cache on later syncs. Changed disk manifests trigger npm
reconciliation; npm may update the guest lockfile, which you can explicitly save back to disk.
The cache belongs to the **active project**, not a collection of isolated per-folder installations.
Save manifests before switching folders. Use **Save now** separately to preserve VM dependencies
and database state in a machine checkpoint; disk manifests alone let you reinstall the packages.
Do not install packages concurrently with source sync or compilation. Interrupted installs retain
an incomplete marker and are reconciled before the next build; compiler/npm descendants are stopped
as a process group. Forced termination during lock acquisition can require manual lock recovery
in the disposable VM; unknown lock ownership is never silently treated as permission to overwrite.

This first workflow targets **public npm-registry packages** for one root project. A registry-specific
browser adapter removes npm metadata/conditional headers rejected by CORS preflight; tarball
integrity is still checked by npm. Authenticated registries, workspaces, local-file/Git dependencies,
and installation lifecycle scripts are not established supported workflows. Package install scripts
are disabled; packages requiring native compilation or postinstall downloads need a rebuilt image.
Prefix/global overrides are refused for managed `/workspace` operations. Other browser network/CORS
restrictions still apply. Optional peer-version warnings are separate from registry transport errors.

Installing a package does not make Node-only APIs available to the client SPA. For example,
`msn-weather` is deprecated and imports Node's `https`; it is not directly usable from a browser
Svelte component. Generated source files from other guest tools are also not exported by the manifest
button: edit/generate source in your local editor, or explicitly export guest edits yourself.

You can run checks from the guest after a sync:

```sh
node --run check
# The original Supabase example's notes commands are also available:
notes signup ada@example.com lovelace-1815
notes add hello
notes ls
```

Native editing tools can also run `npm ci`, `npm run check`, and `npm run dev` on your computer
if desired, but that optional host dev server is NOT what the browser preview uses. Supabase
configuration is provided by the VM preview endpoint, not a public cloud project or localhost port.

## How the networking works

```text
preview iframe in the VM page: <example>/__preview/<owning-client-id>/…
  -> service worker (never host network / never cache)
  -> MessageChannel to the owning VM tab
  -> Armless.connect(8091), bounded JSON RPC
  -> static SvelteKit build OR guest-local Supabase Auth/Data API
```

The SvelteKit app is a **client-side SPA** (`ssr = false`, adapter-static fallback `index.html`).
Each build sets its base path to the current owning tab's private preview route, including any
hosting prefix such as `/snowglobe/`. The same route handles assets, deep links, Auth requests and
all REST methods/bodies. Only the anonymous key is sent to the app. Database credentials, service-role
and secret keys are not exposed by the config endpoint and are removed from the compiler/controller
environment. The unchanged notes migration enables per-user row-level security for create/read/delete.
It deliberately has no update policy: update requests do not modify notes, even for their owner.

No socket listens on your computer, and the static hosting service does not receive these requests.
A copied preview link cannot boot/access someone else's VM: its browser-assigned owner ID must
resolve to the exact VM page in the same browser. Closing the owner tab gives a local 503, with no
fallback to the hosting server. The routing survives service-worker restarts and `snowglobe pwa`.
A page refresh assigns a new owner ID and requires another sync/new preview link. The notes app's
auth storage is scoped to that route; sign in again after reopening the VM. Database contents live
in the VM, so use **Save now** separately to preserve them in a machine checkpoint.

**This is private routing, not an untrusted-code security boundary.** Preview code runs on the
same web origin as the Snowglobe page. Use only your own trusted projects: their JavaScript can
access that origin's browser storage, and project build scripts are executable guest code.
The selected folder handle is readable/writable by the page after permission; trusting the site is
necessary. Do not open untrusted templates or third-party projects in an origin holding sensitive
saved work. Preview code can make ordinary external browser requests, subject to browser rules.
No SSR, SvelteKit server routes/actions, WebSocket proxy, OAuth redirect flow, Storage or Realtime
service is included in this initial example. Use the included Auth/email-password and REST API.

## Disk and checkpoint rules

- Disk sources are authoritative. Sync never writes them; guest/terminal source edits are replaced
  by the next sync. Export such edits manually if you need them on disk. The sole package exception
  is the explicit **Save package manifests to disk** action; sync refuses unsaved VM manifest changes.
- Imports skip `node_modules`, `.git`, `.svelte-kit`, `build`, `dist` and `.snowglobe` directories.
  Imports are bounded to **1 MiB per file**, **16 MiB total**, **1,000 entries**. Binary files are
  imported unchanged. Do not put machine session bundles in your source project folder.
- Do not save files concurrently with sync: the browser cannot take an atomic snapshot of an OS
  directory. Complete local editor writes, then sync; sync again if files changed during import.
- The remembered handle/lock is separate from whole-machine save storage, and scoped to this
  origin/demo path/browser profile. It is not an OS-wide lock on the physical directory.
- Invalid/oversized scans do not reset the guest. An import failure can leave a partial VM mirror;
  disk is unchanged. A compiler failure keeps the previous successful build, but hides Open preview
  until a successful retry. Sync unloads the embedded preview before importing; a separately
  copied preview link may still serve the last good build, but background-tab throttling makes
  that layout unsuitable for reliable Auth requests.
- Only a completed **Save now** preserves VM/database changes. A checkpoint is not a Postgres backup
  service. Ordinary disk files do not depend on saving the VM.

## Deployment and checks

The example is in `DEMOS` in `mise.toml`, with a source-compilation/preview/Auth/REST/RLS check in
`.github/workflows/pages.yml`. The existing main-branch workflow publishes the whole static output
at `/fullstack-supabase-svelte/`; the index includes a launch entry. Deploy the whole generated
folder over HTTPS, including both workers, runtime, snapshot and filesystem blobs.

```sh
go test ./...
node --test internal/site/*.test.cjs examples/editor/bridge.test.mjs examples/fullstack-supabase-svelte/*.test.mjs
cd examples/fullstack-supabase-svelte/app && npm ci && npm run check && npm run build
```

For a built VM, `node /opt/svelte/verify.mjs` exercises the same guest RPC used by the browser:
loads starter sources, builds a prefixed SPA, serves HTML, exposes anonymous-only configuration,
and proxies Auth health and anonymous/RLS-protected notes. Browser verification must additionally
exercise the actual service-worker route and disk picker/native editor workflow.

`bridge.mjs`, the notes migration and native Supabase Dockerfile/startup portions are copied from
existing examples so this remains a standalone Docker build context. The notes helper retains the
original commands and Auth/REST requests, but uses Node's standard filesystem APIs and native
TypeScript support. This avoids the embedded Bun runtime's unsupported ARM CRC instruction crash;
it does not change the pinned Supabase CLI, backend services, password hashing or RLS. New session
files are readable/writable only by the guest user. CLI checks require successful guest exit status,
not just printed results. Regression tests cover the helper and prevent the filesystem bridge from
drifting from the shared editor's validated protocol.
